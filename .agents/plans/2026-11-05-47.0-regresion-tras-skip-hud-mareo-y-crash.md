# Plan 47.0 — Regresión tras el skip: HUD en la cinemática, mareo y el crash «caminando»

El jugador comparte una grabación (`Grabación de pantalla 2026-11-05 170546.mp4`,
22:05:21→22:05:46.7 Z) de una partida con la build servida
`v=2026-11-05-45.0-T5` y reporta tres cosas que antes no pasaban:

1. **T1** — Al saltar la **primera** cinemática se ve toda la UI del modo libre
   (minimapa, estrellas, arma). «Nunca ha funcionado de esta forma».
2. **T2** — Al saltar la **segunda** cinemática aparece el personaje en el punto
   de inicio con el efecto de **mareo** (vaivén + borroso) que «aún no se quita».
3. **T3** — Unos segundos después, **caminando sin hacer nada**, el juego
   **crashea**.

Pide validar la causa, ofrecer las soluciones en un plan nuevo y **no tocar
código del juego en este paso**. Eso se ha hecho: ningún fichero del árbol
`src/`, `vendor/` o `gta_vc_browser/{streamed,bootseed,web}` ha sido modificado
en esta investigación.

Todo número de este plan está medido hoy (05/11/2026) sobre la traza real de la
sesión (`gta_vc_browser/web/odtrace.log`, 22:05:21→22:06:47 Z; UTC) y sobre el
árbol servido. La grabación está alineada con la traza por el rótulo
`SCRTXT3 ... "Saco la cabeza del agujero..."` (22:05:29.693 Z ↔ t≈9 s del
vídeo); el nombre del fichero del vídeo es la hora de **cierre**, no de inicio.

## 1. T1 — La UI aparece al saltar la cinemática

### Mecanismo (leído y medido)

En VC el HUD **no tiene un gate de cinemática**: se oculta como efecto
secundario de la carta ancha.

```
src/renderer/Hud.cpp:340   if (m_Wants_To_Draw_Hud && !TheCamera.m_WideScreenOn) {
```

El T117 que yo metí para quitar el eco de blur/zoom apaga la carta ancha en el
salto:

```
src/animation/CutsceneMgr.cpp:314-320
	if (bCamLoaded) {
		ms_cutsceneTimer = TheCamera.GetCutSceneFinishTime() * 0.001f;
		TheCamera.FinishCutscene();
		TheCamera.SetWideScreenOff();   // <-- quita el único flag que ocultaba el HUD
	}
```

La traza lo encadena exacto:

```
22:05:25.126Z  CUTSKIP  ... red=30.0 wide=1 drunk=0.000
22:05:25.376Z  MAREO    ... wide=0 red=0.0          <- la carta ancha se apaga
22:05:29.693Z  SCRTXT3  texto="Saco la cabeza del agujero un jodido segundo y el destino, ^me"
```

Desde 22:05:25.376 hasta el final del rótulo, el juego sigue en cinemática
(`PEDCAM modo=15` = `CCam::MODE_FIXED`, enum en `src/core/Camera.h:39-54`) y sin
embargo `m_WideScreenOn = false` → `Hud.cpp:340` deja pasar el HUD. Los
fotogramas extraídos del vídeo (t≈5-8 s) muestran minimapa, estrellas y arma.
En la sesión anterior (22:03:32.339 Z, mismo `CUTSKIP`) ocurre idéntico.

### Soluciones propuestas

**S1-a (recomendada, 1 línea + 1 include)** — Gatear el HUD por el estado de la
cinemática y no por el letterbox, en `src/renderer/CutsceneMgr.h:40-43`:

```
src/renderer/Hud.cpp:340
- if (m_Wants_To_Draw_Hud && !TheCamera.m_WideScreenOn) {
+ if (m_Wants_To_Draw_Hud && !TheCamera.m_WideScreenOn && !CCutsceneMgr::IsRunning()) {
```

* `ms_running` es `true` desde `CutsceneMgr.cpp:383` y sólo lo apaga
  `DeleteCutsceneData()` (`:536`), justo la ventana de cola del skip. En modo
  libre normal vale `false`, así que no toca el HUD del juego.
* El borrado está garantizado aunque el guion tarde: `src/core/World.cpp:1776`
  ya llama a `DeleteCutsceneData()` si `HasLoaded()`.
* Ventaja: conserva el arreglo T117 (sin eco de blur/zoom) y devuelve el
  comportamiento de siempre (HUD oculto durante toda la cinemática y su cola).

**S1-b (alternativa, coste cero pero pierde T117)** — quitar el
`SetWideScreenOff()` de `FinishCutscene()`. Vuelve el borrado tardío y el zoom
de cinemática colado en el juego, que es exactamente lo que el T117 cerró. **No
recomendada.**

**S1-c (si S1-a se queda corta)** — además de `IsRunning()`, sumar
`!CGame::playingIntro` en el gate. Aplicarla sólo si la prueba con `HUDGATE`
(S5) muestra algún fotograma con UI visible y `IsRunning()==false`.

### Instrumento de validación

**S5 — `HUDGATE`** (traza nueva, sólo `__EMSCRIPTEN__`, cadencia 500 ms y tope
200 filas, en `Hud::Draw` antes del gate):


## 2. T2 — El mareo que aparece tras saltar la 2ª cinemática

### Qué es (medido, dos sesiones)

No es la carta ancha: el T117 la apaga bien (`wide=0 red=0.0`). El resto es
`CMBlur::Drunkness`, que vale `m_nDrunkenness / 255`:

```
22:05:25.821Z  MAREO  drunk=0.000 wide=0        <- tras el 1º skip, limpio
22:05:30.443Z  PEDCAM modo=15 ... wide=1 red=30 shake=0.00 drunk=1.000 fade=255
22:05:30.693Z  MAREO  drunk=0.980 wide=0 red=0.0
22:05:36.260Z  MAREO  drunk=0.322               <- aquí muere el proceso (T3)
```

Sesión anterior, mismo patrón: `CUTSKIP` 22:03:32.339 → `drunk=0.969` en
22:03:37.622 y decaimiento igual. **Las dos veces que se salta la 2ª
cinemática, la embriaguez salta de 0 a ~1.0 en unos 5 s.**

El vaivén y el borrón son los dos consumidores de ese valor:

* `src/core/Camera.cpp:549-572` — con `Drunkness > 0` multiplica `FOV *=
  (1 + Drunkness)` (hasta ×2) y desplaza `CamSource/CamUp/CamFront` con la tabla
  de balanceo → el movimiento lateral lento que describe el jugador.
* `src/extras/postfx.cpp:595-665` — `CPostFX::Render` llama a
  `RenderMotionBlur(cam, 175.0f * CMBlur::Drunkness)` **aunque**
  `EffectSwitch = POSTFX_OFF` (`sw=0` en la traza) → el fantasma/borroso.

### Quién lo mete

El único escritor de `m_nDrunkenness` en el motor es el comando de guion:

```
src/control/Script7.cpp:893-901
	case COMMAND_SET_PLAYER_DRUNKENNESS:
		ScriptParams[1] leídos del SCM
		pPlayerInfo->m_pPed->m_nDrunkenness = ScriptParams[1];
		pPlayerInfo->m_pPed->m_nFadeDrunkenness = 0;    // <-- apaga mi decaimiento T115
```

(Opcode en esta build: 1325 = `0x052D`, contado sobre el enum de
`src/control/ScriptCommands.h:1332`. Los otros escritores son los resets:
`GameLogic.cpp:378-381` al resucitar, `Script.cpp:411` (`ClearForScript` pone
`m_nFadeDrunkenness = 1`), `PlayerPed.cpp:650-652` al crear el ped.)

Es decir: **el mareo lo pone el `main.scm`**, y el `m_nFadeDrunkenness = 0` de
esa misma línea desactiva el decaimiento que añadí en T115; sólo vuelve a
decaer cuando `ClearForScript()` lo reactiva. Por eso dura ~8 s y no
indefinidamente (en esta sesión no llegó a 0 porque el proceso murió antes).

**Lo que NO está resuelto (y no debe decidirse a ciegas):** si ese
`SET_PLAYER_DRUNKENNESS` del tráiler/barco del inicio es *intencionado* en el
guion original (el balanceo del barco en la tormenta) o si es una cola que el
skip deja sin su `= 0`. El escáner estático sobre `streamed/data/main.scm` no
lo cierra (la cabecera no es el formato que esperaba mi parser;
`streamed/data/main.sc` es sólo un script de pruebas de 5.7 KB).

### Soluciones propuestas

**S2-a (obligatoria antes de tocar nada) — `DRUNKSET`** en
`src/control/Script7.cpp:897`, 6 líneas de traza:

```
DRUNKSET val=%d op=%d script=%s thread=%d pos=%.1f,%.1f,%.1f en_barco=%d agua=%d fade=%d
```

Con una partida se sabe qué hilo del guion lo dispara, con qué valor y si el
jugador está realmente en el barco. Es la pieza que falta para elegir entre
S2-b y S2-c. **Sin este dato no se toca el mareo.**

**S2-b (si resulta ser cola del skip) — reset en el handoff**: en
`CutsceneMgr::FinishCutscene()` (`:320`, junto al `SetWideScreenOff`) y en
`DeleteCutsceneData()` (`:533`):

```
	FindPlayerPed()->m_nDrunkenness = 0;
	FindPlayerPed()->m_nFadeDrunkenness = 0;
	CMBlur::ClearDrunkBlur();
```

Cuesta 3 líneas, es simétrico con lo que ya hace `PlayerPed.cpp:650-652` y
mata el mareo en el mismo fotograma del salto. Riesgo: si el guion lo vuelve a
poner para el barco, sólo se corta la cola (comportamiento deseado igualmente).

**S2-c (si el efecto es intencionado pero excesivo) — tope de sensación**: en
`src/peds/PlayerPed.cpp:3414-3435` limitar el valor que se entrega al render,
sin borrar el del guion:

```
	float odDrunk = min(m_nDrunkenness / 255.f, 0.25f);   // antes: /255 cru
	CMBlur::SetDrunkBlur(odDrunk);
```

Mantiene el balanceo del barco pero quita el ×2 de FOV y el blur a 175.
Params del sway no se tocan.

**S2-d (higiene, sin efecto visual)** — `add=150` (`TheCamera.m_imotionBlurAddAlpha`,
escrito en `Camera.cpp:4275`) aparece en todas las filas `MAREO` y no lo lee
nadie del render: o se consume o se quita del instrumento, porque ahora
`odAbnormal` salta siempre y la sonda no discrimina.

## 3. T3 — El crash «caminando»: dos índices de `gta3.img` distintos

### Prueba de la causa (medida sobre el árbol y la traza)

El backend suelto vive de **un único** fichero índice, `models/gta3.dir`
(registros de 32 B: `start:u32, sectors:u32, name:24`), y **el mismo** fichero
lo usan las dos mitades del sistema:

* `CStreaming::LoadCdDirectory()` (`src/core/Streaming.cpp:492-494, 569`) →
  posición/tamaño de cada modelo (`SetCdPosnAndSize`).
* `CdStreamPosix.cpp:745-801` (registro) + `OdDoRead()` (`:184-270`) → a qué
  fichero suelto se abre cada sector pedido.

Hay **dos copias** del índice y son distintas:

| | `streamed/models/gta3.dir` | `bootseed/models/gta3.dir` |
|---|---|---|
| tamaño / entradas | 195 072 B / 6096 | 195 072 B / 6096 |
| sectores totales | **178 498** | **178 489** |
| entradas con `start`/`sectors` distintos | — | **5169 de 6096** |
| `start` duplicado (alias) | **0** | **78** |
| sectores vs tamaño real de sus ficheros | 0 discrepancias | 0 discrepancias |
| ficheros en `models/gta3.img/` | 6085 | 1762 |

Los 1762 ficheros que existen en **ambos** árboles son **byte a byte idénticos**
(md5), así que el layout de `streamed` es válido para los dos. La copia del
bootseed **no** deriva del layout servido: tiene 9 sectores menos repartidos y
78 colisiones.

Y en MEMFS gana el del bootseed, porque `bootseed.list:1` es
`models/gta3.dir` → se hornea en `web/public/build/reVC.data`
(169 874 219 B, 16:49) → al arrancar el fichero ya existe y `ondemand.js` nunca
va a por el de `/streamed/`. **Índice en memoria = bootseed; bytes = streamed.**
Las colisiones son el mecanismo exacto del crash. Con el índice del bootseed:

```
sec=46578  dueño: veg_palmbig14.dff (46578,3)  Y  veg_palmkb2.dff (46578,2)
sec=71705  dueño: LODchbt.dff (71705,3)        Y  LODcland05.dff (71705,1)
sec=71856  dueño: LOD_mansionbase02.dff (71856,2)  Y  LOD_road06.dff (71856,1)
sec=45854  dueño: LODxrefhot.txd (45846,16)    Y  od_beachstuff.txd (45854,24)
```

`OdDoRead` devuelve el primer dueño, así que el motor pide
`veg_palmkb2` y le llegan bytes de `veg_palmbig14`. La traza lo dice con el
`posn` (idéntico al del bootseed, no al del streamed):

```
22:05:26.196Z  [od] buf falla LODcland05    posn=71705 head=10000000 03100000 ffff0310
22:05:26.202Z  [od] buf falla LOD_road06    posn=71856 head=10000000 d10a0000 ffff0310
22:05:29.193Z  TXDGARBAGE wshxrefhirise posn=46100   (streamed dice 46122)
22:05:30.193Z  TXDGARBAGE strpclbsgns  posn=93286   (streamed dice 93308)
22:05:30.693Z  TXDGARBAGE od_beachstuff posn=45854  (streamed dice 45876)
```

Decodificando el `head`: tipo `0x10` (STRUCT), `chunkSize = 0x1003 = 4099 B`
para un objeto que el índice dice de 1 sector (2048 B), versión `0x1003ffff`.
El chunk pide el doble del búfer; librw sigue caminando y el `malloc` recibe un
tamaño basura:

```
22:05:36.410Z … 137 filas JSERR_REJ "memory access out of bounds"
   emscripten_builtin_malloc ← rw::malloc_h ← rw::FrameList_::streamRead
   ← rw::Clump::streamRead ← RpClumpStreamRead ← CFileLoader::LoadAtomicFile
   ← CStreaming::ConvertBufferToObject ← ProcessLoadingChannel ← RetryLoadFile ← Update
22:05:38.714Z … variante: rw::mustmalloc_h ← RwStreamOpen ← ConvertBufferToObject
22:05:38.7 → 22:06:47.2  sin una sola fila de traza (98.7 s de zombie, canvas congelado)
22:06:47.232Z  ENGSTDOUT [web] state -1 -> 0 @ tick 0     <- rearranque en caliente
```

Es decir: el jugador no «crasheó por caminar»; el crash es el del streaming de
siempre (T17/ADR-044) disparado porque ese sector del mapa se resolvió contra
un índice viejo. Por eso **T17 pasa a estar causado**.

Detalles que **no** son el crash, para no arreglar de más:

* Los 4 `ODSHORT short` (kaufman 168 488/169 984, peren, faggio, hermes) son el
  **último sector parcial** de ficheros cuyo `ceil(size/2048)` coincide con el
  índice: benignos. El relleno a 0 de `OdDoRead` es correcto en ese caso y no
  hay que tocarlo.
* Sí es un defecto real el *tramo* de `OdDoRead`: un déficit ≥ 1 sector entero
  (bytes de otro objeto) se rellena a 0 y se devuelve como éxito; eso convierte
  un error duro en un objeto corrupto que revienta el heap.
* `FAIL model veg_palmkb2` ×59 en 10 s: `Streaming.cpp:697-731` hace
  `RemoveModel + ReRequestModel` sin tope → reintenta el mismo sector mal
  resuelto cada frame de carga.

### Por qué se rompió el índice del bootseed (pregunta del jugador, 18:40)

El detonante es el 45.0 T6, pero **no son los DFF**: los 1762 ficheros que hay
en los dos árboles son byte a byte idénticos, y todos los DFF servidos son RW
3.3 válidos. Lo que se rompió fue la **copia del índice** que el 45 rehizo.

Medida la forma de los dos índices (recorrido acumulativo `start[i] ==
start[i-1] + sectors[i-1]`):

| | `streamed/models/gta3.dir` | `bootseed/models/gta3.dir` |
|---|---|---|
| saltos de continuity | **0 huecos, 0 solapes** (6095 contiguos) | **367 huecos + 368 solapes** |
| entradas con `sectors` distinto vs streamed | — | **8** |
| deriva acumulada al final | 0 | **+22 sectores** (y 9 menos en el total) |

Las 8 entradas con tamaño distinto son exactamente los vehículos que el split
de lente agrandó hoy (mtime 2026-11-05, y los 8 **ya no existen** en
`bootseed/models/gta3.img/`): `barracks` 66→68, `hotrinb` 102→103, `lovefist`
100→101, `mrwhoop` 82→83, `romero` 103→104, `sandking` 96→97, `stretch`
94→95, `zebra` 98→99. Suman **+9 sectores**, que es justo la diferencia de
totales.

La deriva, sin embargo, cambia en **737 posiciones** distintas del índice (no
en 8), y ahí está el defecto de herramienta: `repack_dir.py` recalculaba el
`.dir` **recorriendo su propio árbol**. Con `streamed/` (6085 ficheros) el
resultado es contiguo y correcto; con `bootseed/` (1762 ficheros) no puede
medir los 4323 ausentes, parchea tamaños sueltos y deja un layout con huecos y
solapes. Por eso el arranque de hoy llevaba dentro del `.data` un índice que
asignaba el mismo sector a dos modelos.

Consecuencia para el plan: S3-a (copiar el índice bueno) es **necesaria y
suficiente** para el estado de hoy, y S3-b (validator) es la que impide que
`repack_dir.py` vuelva a escribir un `.dir` no contiguo en el bootseed.

### Soluciones propuestas

**S3-a (datos, 0 líneas de C++, es la que cierra el crash)** — que
`bootseed/models/gta3.dir` sea **copia byte a byte** de
`streamed/models/gta3.dir`:

1. `copy streamed/models/gta3.dir bootseed/models/gta3.dir` (verificar md5
   igual).
2. Regenerar el índice de datos y el manifiesto: `python
   gta_vc_browser/tools/gen_manifest.py`.
3. **Rehacer `reVC.data`** (`bash gta_vc_browser/build.sh`) porque el índice
   viejo está horneado dentro del `.data`; sin este paso el arreglo no llega al
   navegador.
4. Subir el contador compartido `VERSION`/`dataTag` en
   `gta_vc_browser/web/lib/index.js:267` (o `ondemand.js:179` `dataTag`) para
   que IndexedDB purgue el `.dir` y los DFF cacheados. **Ojo: `VERSION` es un
   contador compartido con el carril de vehículos; se sube, no se pisa el
   texto del otro carril** (memoria del proyecto).

*Comprobación de intentos previos:* `ondemand.js:174-178` (45.0 T6) dice que
`repack_dir.py` rehizo «streamed y bootseed» — pero el resultado medido es dos
índices distintos, o sea que el repack del bootseed se hizo **contra su propio
árbol parcial** en lugar de copiar el del streamed. Ese es el bug de
herramienta a corregir.

**S3-b (guardia de build, necesaria para que no vuelva)** — script nuevo
`gta_vc_browser/tools/check_img_index.py`, duro en `build.sh` (falla la build):

* el índice streamed es bien formado: `start` estrictamente creciente y
  **contiguo** (`start[i] == start[i-1] + sectors[i-1]`), `sectors ==
  ceil(tamaño/2048)` contra `streamed/models/gta3.img/`, 0 alias, `n` entradas
  == nº de ficheros;
* `md5(bootseed/models/gta3.dir) == md5(streamed/models/gta3.dir)`;
* `models/gta3.dir` está en `bootseed.list` y en `manifest.json` con el tamaño
  del streamed;
* sale un informe con las entradas mal (hoy: 5169 distintas, 78 alias, 367
  huecos + 368 solapes).

Y el arreglo de herramienta que evita la recaída: **`repack_dir.py` deja de
recalcular recorriendo su propio árbol** — calcula el layout una vez contra
`streamed/models/gta3.img/` y escribe el mismo bytes en la copia del bootseed.
(Sobre el árbol parcial de 1762 ficheros no puede medir los 4323 ausentes, y es
lo que generó los huecos/solapes.)

**S3-c (endurecimiento del motor, 2 cambios pequeños)** — que un índice roto no
pueda tumbar el proceso:

1. `src/core/CdStreamPosix.cpp` `OdDoRead()`: si el déficit del `read` es ≥
   `CDSTREAM_SECTOR_SIZE`, **devolver fallo** (no rellenar y dar éxito). El
   último sector parcial sigue rellenándose como ahora.
2. Antes de `CStreaming::ConvertBufferToObject`, validar la cabecera RW contra
   el tamaño del búfer (tipo `0x10`/`0x16`/TXD mágico y que el primer
   `chunkSize` quepa) y si no, ir por el camino `FAIL model` existente. Esto
   convierte el `memory access out of bounds` en un modelo que no carga — que
   es lo que ya hace `Streaming.cpp:697-731` y lo que salvó la partida en T21.

**S3-d (bajar el ruido que queda aunque falle un modelo)** — tope de reintentos
en `Streaming.cpp:697-731`: máximo 3 por `streamId` y luego marca el modelo
como no-cargable en la sesión con una sola fila `FAIL model ... x3`, en vez de
59 reintentos en 10 s (`ReRequestModel` con enfriamiento ya existe,
`OdCoolingDown`; falta el tope duro).

### Validación de T3 (sin jugar)

**S3-e — `DIRTAG`** (traza nueva en `CdStreamPosix.cpp:784-792`, junto al
`addimage ... LOOSE` ya existente): `n`, `totalSectors` y los primeros 8 bytes
/md5 del `.dir` leído. Hoy debería imprimir 178 489; tras S3-a, 178 498. Con
eso el arreglo se confirma **en la primera arranque**, sin depender del jugador.

**S3-f — prueba offline**: `python -c` que simule `OdDoRead` sobre el índice
nuevo y compruebe que los `posn` que salen en la traza de esta sesión
(71705, 46100, 93286, 45854, 71856) resuelven a su propio modelo.

## 4. Hallazgos extra (mismas trazas, coste bajo)

**S4-a — ficheros que faltan en MEMFS (errno=44)**. 4 filas `ODSHORT open-fail`
(`od_tracks05.dff`, `ocmiamistrip7.txd`, `deco_polgrnda9.dff`,
`odnanrod2b_nt.dff`) para nombres que **sí** están en disco y en el manifiesto:
o nunca se aseguraron o los desalojó la política de `OD.live`
(`ondemand.js:300-310`). Propuesta: en el `open` con ENOENT, pedir
`OD.ensure(path)` (Asyncify) antes de dar fallo, y trazar `evictado` vs
`nunca-fetch`. Es distinto del crash: aquí el modelo no carga, no revienta.

**S4-b — `JS ODMISS fuera-de-manifest` ×21 en 3 s** (`white64`, `black64`,
`neonh1`, `ws_alley_conc1`…): el motor prueba 3 extensiones por textura
desconocida y cada prueba es un round-trip asíncrono perdido. Propuesta:
caché negativa por nombre en `ondemand.js` (una sola consulta por nombre y
sesión). Ahorro directo de latencia de streaming, en el carril de rendimiento.

**S4-c — la rotación de logs miente**. La línea de rotación promete

**S4-d — fase S / FPS sin atribuir**. Esta sesión sólo alcanzó 1 `SNDTOP` y 90
`RGPASS` antes de morir la traza, y la ventana muestreada es de cinemática con
fade (`FPHASE ... S=0.0 wait=20.1 dc=0`), no representativa. El T24 queda
abierto y **depende de S3-a**: sin crash se puede capturar una sesión de 2-3
minutos jugables y recortar el pase caro.

## 5. Orden de ejecución propuesto

Cada paso = una build y una comprobación; ninguno toca el carril de vehículos
salvo el punto 4 de S3-a, que es el contador compartido.

1. **S3-a + S3-e** (datos + `DIRTAG`) → cierra el crash (T3) y desbloquea todo
   lo demás. Verificar: `DIRTAG total=178498`, `check_img_index.py` en verde.
2. **S3-b** (`check_img_index.py` en `build.sh`) → que no pueda volver.
   Verificar: romper a propósito el `.dir` del bootseed y ver fallar la build.
3. **S1-a + S5** (`Hud.cpp:340` + `HUDGATE`) → cierra T1.
   Verificar: dos skips, `HUDGATE cutrun=1` con el HUD fuera y `wide=0`.
4. **S2-a** (`DRUNKSET`) → mide antes de decidir; **pausa obligada**: con esa
   traza se elige S2-b o S2-c y se decide con el jugador.
5. **S3-c + S3-d** (cabezal RW, déficit ≥ 1 sector, tope de reintentos) → que
   un índice roto nunca más derribe el proceso.
6. **S4-a → S4-b → S4-c** → higiene de red y evidencia.
7. **S4-d** con todo lo anterior: sesión larga para la fase S (T24).

## 6. Restricciones

* Ninguna de las soluciones se ejecuta sin «execute the plan» (puerta de
  autorización del harness; memoria: *plan execution is a separate permission*).
* `tools/`, `src/vehicles/` y los DFF servidos son compartidos con el carril
  41.0→45.0: S3-a sólo toca `bootseed/models/gta3.dir`, `manifest.json` y el
  tag; no reescribe DFF ni scripts de parcheo ajenos.
* Los cambios de C++ van tras `#ifdef __EMSCRIPTEN__` (instrumentos) o son
  neutros en desktop; sin `#ifdef VICEEXT_*` nuevos.
* No se sube el tope de FPS: el objetivo sigue siendo ≤120 estable con 60
  objetivo.
